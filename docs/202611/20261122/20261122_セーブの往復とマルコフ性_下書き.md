## 1. 案

### 案 1（推奨）：欄の比べ＋保存の点を 3 つ（同じプロセス）

- 形：1 本の続けた世界 A を事前の四半期まで進め、保存の点（境＝0 日・45 日・75 日）でそれぞれ保存したバイト列を持つ。A を終わりの日まで進める。各点のバイト列から B_k を 1 本ずつ読み、同じ終わりの日まで進めて A と比べる（同時に持つ世界は今と同じ 2 本）。
- 比べ：SaveGame の FieldsOf（SaveGame.cs:41〜60）を共用する並行の走査（SimCore の internal 関数・シミュは呼ばない）。
  - double はビットで比べる（−0 と NaN の中身も別に数える）。
  - 参照は A→B の対応表で同じ形かを見る（同じ物を 2 か所が指すか）。
  - 辞書と集合は後回しの列に積み、他の全ての欄を歩いた後に鍵で引いて比べる（基本の型の鍵は値で・参照の鍵は対応表で）。順だけが違えば〈順だけ〉の区分に数える（値の違いに数えない）。
  - 出力は違いの一覧（欄の道・A の値・B の値・区分）を先頭の N 件。
- 判定：値の違いが 0 件で緑。順だけの違いと、バイト列の一致は記録。
- 良い所：比べる集合＝保存する集合（分子と分母が同じ関数）。違いの場所が欄の道で読める。事前の 300 四半期は 1 回で 3 点を測れる。別のプロセスが要らない（material §5）。
- 難しい所：走査の関数を新しく書く（SaveGame の書き手とほぼ同じ形・約 100〜150 行〈推〉）。辞書の参照の鍵の後回しを誤ると、順だけの違いを値の違いに数える（突然変異 M3 で確かめる）。300 四半期の世界 2 本の走査の秒〈推：保存と同じ程度＝1〜3 秒〉。

### 案 2：計器の全ての表（別のプロセス）

- 形：Runner の動詞を 2 つ（`savetest-save <種> <四半期> <日> <ファイル>`・`savetest-cont <ファイル> <四半期> <種>`）。前の動詞は計器を切って（Instruments.On＝偽）保存の日まで進め、保存し、その日から計器を入れて続ける。後の動詞は読み込みの直後から計器を入れて続ける。2 つの POB_INSTRUMENTS のフォルダを trial_cmp.py の形で比べる。ident.cfg:93 の KNOWN と、プロセスの static の数えを出す表は除く。
- 良い所：違いが表・列・国・四半期で読める。POB_PAR の並列と逐次の主張も同じ道で確かめられる（後の動詞を POB_PAR=0 で）。
- 難しい所：計器の状態（ConditionalWeakTable・Diag*・Cp*）が保存の日に両方で空から始まる形にしないと必ず赤（Instruments.On を途中で真にする仕掛け＝計器の Phase の warm の初期化も通らない）。比べる集合が計器の見る物だけ。費用は計器つきの 12 四半期の 2 本（〈推〉数十 MB・+10〜20 秒）。Runner の動詞が 2 つ増える（重要でない機能は削減の方針に逆らう）。

### 案 3：バイト列の一致（根から順を揃える）

- 形：形 A のバイト列をそのまま門にし、辞書の順の違いを根から消す（Remove の 5 欄を、消さずに値 0 で残す形や、並べた配列へ置き換える）。
- 良い所：比べの道具が最も簡単（バイトの比べだけ）。
- 難しい所：状態の表現を変える＝読み手の挙動に触れる恐れ（0 の値の行を数える読み手）・Remove の 5 欄を全部直さないと緑にならない・将来の辞書の Remove でまた赤。違いの場所が読めない。**採らない**。
