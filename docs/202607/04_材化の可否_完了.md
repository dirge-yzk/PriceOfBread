# 1. ★財の追加を阻む致命的障害3つ（独立検証済み）

## 1-1. 財の追加そのものが非恒等（思想③が使えない）

検証エージェントが両報告の見落としとして指摘した最重要点：

> **新財を1つ足すと、その財を誰も投入に使わなくても既存「全工場」の Capacity が変わる。**
> 「財追加＝非恒等」は Liebig 以前に労働配分で確定している。

工場の Capacity は労働pop.Size の零和分割で、配分の重みは賃金ではなく需要量。財が増えれば既存工場のシェアが奪われる。

## 1-2. `qtyPerOutput = 0` では休眠にできない

> 需要0の財は `ration = 0` になり、**リービッヒの `min()` がそれを拾って全工場の産出を0にする。**

＝「既定0で厳密恒等に入れ、証明してから点火する」という全新機構に課してきた規律が、
**財の追加にだけは原理的に適用できない**。材化は最初から全開で入れるしかない。

## 1-3. 巡回で `ComputeComplexity` が無音で発散

`Catalog.cs:383-395` は固定24回の反復緩和で**収束判定が無い**。巡回が入ると Complexity がゴミ値になり、
その財と下流全部が**永久に未発明**になる。例外もNaNも出ないので不変量検査に掛からない。

★ 現状 goods.json の inputs グラフに閉路は**0件**（DFSで全 elementary cycle を全数列挙して確認）。
つまり「閉路があるときに収束するか」は**一度も実証されていない**。動力・輸送はまさに閉路を作る財である。

## 1-4. 非巡回で慎重に入れても被害が出る

Complexity が全下流で +1〜+6、技術ゲート財が **13→79** に激増。
**パンの onset が 0→1.40 になり、開始から数十年「パンが作れず・誰も欲しがらない」。**

# 2. ★輸送力は既に8割材化されている

```
線路(56)・機関車(88) を買う → RailCapacity に積む     Transport.cs:66
帆船(84)・汽船(85)   を買う → ShipCapacity に積む     （汽船は ShipTier2CapMult=2.5）
需要 = 重量加重の潜在輸送量 vol ／ 供給 = cap ／ 清算 = LastTradeThrottle
```

**財は既に消費され、需給も清算比率も在る。欠けているのは価格と決済だけ。**

## 2-1. ★距離コストは誰にも支払われない

> `margin = TransportMargin(0.18) × distF` は importThresh/exportThresh を広げるだけの
> **純粋なデッドウェイト**で、船主にも商人にも入らない。**運賃という支払い先が存在しない。**
> （`InternationalMarket.cs:189` / `:292-293`。決済は輸入も輸出も q × 世界価格でしか動かない＝`:318,321-322`）

★ これは**対外国債の片肺と同一の穴**（`Fiscal.cs:185/242/284`＝起債・利払い・償還のいずれにも相手国が居らず、
金がモデル外から湧きモデル外へ消える）。痛む側だけが居て、稼ぐ側が居ない。

## 2-2. だから新財ではなく「運賃をつける」

既存の貨物市場に価格をつけて船主に払う。これで：

- **新財ゼロ** → §1 の致命3つを**全部回避**（Complexity 不変・参照価格不変・労働配分不変・セーブ互換維持）
- デッドウェイトだった距離コストが**所得移転**になる＝保存則の内側に入る
- 英のレンティア化（見えない輸出）が成立

★ 陸上を非貿易に留める設計は既存実装と整合（`RailCapacity` は内陸→港の接続にしか使われず国境を跨がない）。

## 2-3. 決済を両建てにする3条件

対外国債と同じ穴に落ちないために：
①決済を必ず両建てにする ②相手国を特定できる台帳を持つ ③記帳と実マネー移動を同一ステップ内でビット一致させる。

⚠ 未解決の論点：**材化した海運の「封鎖」は誰の raid を適用するのか。**
現状 `CommerceRaidFactor` は荷主国の自国 `ShipCapacity` に掛かる仕様なので、
英船が仏貨物を運ぶ契約ができた瞬間に定義が壊れる。

## 3-1. ⚠ 落とし穴：Service tier にすると死ぬ

`EconomyStep.cs:267-273` の `baumol`（役務かつ非人力）分岐は **boost を 1.0 固定**にする。
新しい Service 財として動力を足すと、**工業化も技術も蒸気も電化も一切乗らない**。
労働力(93)/農業労働力 は `isLabor` で例外扱いされているので、**その並存レシピとして足すぶんには問題ない**。

## 3-2. ⚠ 未解決：水力の立地上限

「州ごとに上限がありスケールしない」既存前例は2つだけ——
`ArableLand`/`LandFactor`（軟らかい収穫逓減）と `GridCapacity`（硬い比例配給）。
**どちらも一次データ由来ではない**（`world.json` の `resources` は有無だけで量を持たない＝

## 3-3. 現行の Steam/Elec は雑なバフではない

排除候補として実際に取れるのは `SteamBoost`・`ElecBoost` の2因子＋`ElecLaborSave` のみ。
残り13本強は動力と無関係（技術・労働時間・組合・鉄道制度・発明時期・労働供給・土地の肥沃度・
軟予算制約・内戦・規模の経済・賦存・天候・鉱床）。

そして Steam/Elec は**採算ゲート＋技術ゲート＋慣性(FillInertia)＋不可逆性(ElecFillIrreversibility=1.0)
＋送電容量クランプ**を備えた採用モデルで、潰すと失うものがある。

★ **さらに「財→バフ」の逆転前例が1件あり、それが動力そのもの。**
2026-06に「全機械化工場が1789から無条件で石炭を焚く」を**撤廃して**
技術onset＋採算ゲート＋SteamBoost＋SteamFill慣性へ置き換えた（理由＝時代錯誤の是正）。
動力の Input 化は**一度通った道を戻ることになる**。

## 4-3. ⚠ 訂正：BasinOverride は海路距離を変えない

`Geo.SeaDistanceKm` は `World.Basin` を読まず、生の緯度経度から毎回判定する。
潰れるのは距離ではなく**輸送マージン**——`InternationalMarket.cs:161` の `distF[i]` という
**国単位1本の係数**に封鎖ペナルティ0.8が載り、`:189` で全州に一律に乗る。

## 4-4. ⚠ 罠：`Geo.BasinOf` に黒海矩形を足してはいけない

`Geo.cs:27` の `IsWestern` は `Atlantic or Mediterranean` のみを西方とし **BlackSea を含まない**。
`Geo.cs:46` のコメントは「大西洋系（大西洋/地中海/**黒海**）」と書くが**コードは含んでいない**
（現状 BasinOf が BlackSea を返さないため矛盾が露見していないだけ＝型F/型Eの親戚）。

矩形を足した瞬間、黒海の点↔大西洋の点の海路が**喜望峰/スエズ/パナマ迂回**になる。
`Geo.ColonyCoord("ボスポラス") = (41.0, 29.0)` は矩形の内側なので、
征服で本国が大西洋国（英仏）へ移ると維持費が突然ケープ迂回になる。

★ なお **ロストフ(lat 47.24) は Mediterranean 矩形（lat 30-46）の外にわずか0.24度**。

## 4-5. Basin は再計算されない

書き手は `Simulation.cs:112` の1箇所のみ＝**構築時に一度決まったら、征服・遷都・州の獲得喪失で更新されない**。

## 4-6. ⚠ ウラジオストクは1860年創建

初期州に置けない。露の `frontiers` に既に**ウラル／シベリア**があるので、その延長が素直。

ただし蝦夷地は **frontier と抽象侵略標的の Power で二重定義**されている（`world.json:177-186` と `:4400-4416`）ので、
踏襲するならその重複を踏まないこと。
