# 発注と生産の分離 — 再点火トリクルの物理化

**日付**：2026-08-01
**対象**：`PriceOfBread.SimCore/EconomyStep.cs`（中核）／`Coefficients.cs`／`Invariants.cs`（計器）
**位置づけ**：作者裁定「`ReignitionTrickleConserves` と `CurrentInputFillGates` は恒久0＝これは不具合ではなく実装である。ただし**同等またはよりリアリティのある挙動を確保できるなら、より良い実装に差し替えてほしい**」への回答。

---

## 0. 一文の要約

**「発注（買う約束）」と「生産（物理）」を別の量から読む行為として分離し、現行の再点火トリクルを「需要量を1単位も変えないまま、引き取った物には必ず代金を払う実需要」へ格上げする。** — 幽霊需要を消すのではなく、幽霊から「代金の伴わない物量消滅」という物理の不正だけを剥がす。

---

## 1. 置き換える対象（現行 hack が何をしているか・なぜ差し替えるのか）

### 1.1 現行の実体（経路で示す）

`EconomyStep.Run` の「**② 工場の投入需要**」ループ（全生産者を回る。`Bankrupt` を除外しない）：

```
eq      = EffectiveQty(s, inp, coef)
inputNeed[inp.GoodId]    += s.Output * eq                                      // 物量を伴う本体
trickle = Max(0, ReignitionDemandFrac(0.03) * s.DesiredOutput - s.Output) * eq
inputTrickle[inp.GoodId] += trickle                                            // ★これが幽霊
```

「**③ 各財の取引**」ループで、既定（`ReignitionTrickleConserves = 0`）ではこれがコア需要に混ざる：

```
coreDemand = popDemand + inputNeed + investDemand + militaryDemand + (1 - Conserves) * inputTrickle
coreSold   = Min(available, coreDemand)          // available = m.Stock + produced[gi]
ration[gi] = coreSold / coreDemand               // ← 分母が膨らむ＝真の買い手の充足率が薄まる
sold       = coreSold + effSold
m.Stock    = Max(0, available - sold)            // ← trickle*ration ぶんの実物が在庫から引かれる
```

一方、「**工場の投入支払い**」ループが払うのは `s.Output` ベースのみ：

```
pay = clearPrice[inp.GoodId] * s.Output * EffectiveQty(s, inp, coef) * ration[inp.GoodId]
ic += pay;  revenue[inp.GoodId] += pay
```

### 1.2 幽霊の正体＝**代金の伴わない物量消滅**

毎月 `inputTrickle[gi] × ration[gi]` 単位の実物が在庫から消え、その代金を誰も払っていない。副作用は2系統：

1. **無償在庫消滅**：`revenue[gi]` に入らないので、上流生産者は物を失って代金を受け取らない。倒産・休止した工場が上流の在庫を無償で食っている。
2. **賃金なき雇用**：投入に労働財を持つ工場では労働の `LastSold` が嵩上げされる。`unsold = 1 - LastSold/LastProduced` なので **失業が構造的に過少計上**され、`Politics` の `UnemploymentMilitancy` にそのまま効く。

### 1.3 なぜ既存の2つの休眠係数では直せないのか

- **`ReignitionTrickleConserves = 1`** は trickle を `coreDemand` から**外して捨てる**。消えるのは (i) 幽霊が食っていた在庫吸収（＝過剰在庫の価格下押しを止めていた力）、(ii) `ration` 希釈による配給の分配、(iii) 労働財 `LastSold` 嵩上げ の3つ。**物量が消えるので「代金を付ける」対象そのものが無くなる。** 実測の破局（ハーネス不合格10/10・◎7割帯21→6・逸脱過多13→39・最貧国の満足度0.06）は、経済の物量収支がこの無償消滅の上に較正されていることと完全に整合する。
- **`CurrentInputFillGates`** は「① 供給」ループの `target` にしか触れない産出律速で、②の需要とは触っている場所が別。産出水準そのものの土台を恒常的に下げるのでテストが落ちる。

### 1.4 差し替えの根拠

作者の言＝「実装の**形**としては正、実装**方法**としてはスマートでない」。
本設計は、形（需要量・配給希釈・在庫吸収・価格シグナル・数量再参入）を**1ビットも変えず**、方法（無償収奪 → 正常な購買）だけを直す。したがって「実測の破局」を引き起こす経路が構造的に存在しない。

## 2. 新機構の定義（発注と生産の分離をどう実装するか）

### 2.1 設計の一行

**発注は「買う約束」であって「作る行為」ではない。約束した量は `s.DesiredOutput`（意図）から立ち、生産した量は `s.Output`（物理）から立つ。現行はこの2つが別変数で立っているのに、決済だけが `s.Output` しか読んでいない。** 決済にも意図側を読ませれば、発注と生産の分離が会計として完成する。

### 2.2 機構1（本体）：再点火発注の決済

**新ヘルパー**（`EconomyStep` の private static。`EffectiveQty` / `InputCostPerUnit` と同じ位置）：

```
private static double ReignitionOrderQty(Producer s, Input inp, Coefficients c) =>
    Math.Max(0, c.ReignitionDemandFrac * s.DesiredOutput - s.Output) * EffectiveQty(s, inp, c);
```

**② のトリクル行をこのヘルパー呼び出しに置換する**（式・評価順・値がすべて同一＝ビット恒等）。以後、②と決済が同一のヘルパーを呼ぶので**式のドリフトが原理的に起こらない**。

**「工場の投入支払い」ループの inner loop 内**、`revenue[inp.GoodId] += pay;` の直後に1ブロック追加：

```
if (coef.ReignitionOrderSettles > 0)
{
    double oq   = coef.ReignitionOrderSettles * ReignitionOrderQty(s, inp, coef);
    double opay = clearPrice[inp.GoodId] * oq * ration[inp.GoodId];
    ic += opay;  revenue[inp.GoodId] += opay;
}
```

**★実装上の絶対条件（3点。守らないと恒等が壊れる／無音のズレが入る）**

1. **既存の `pay = clearPrice[...] * s.Output * EffectiveQty(...) * ration[...]` の行は1文字も変えない。** 綺麗にまとめて `pay = clearPrice * (s.Output * eq + oq) * ration` と書くと、IEEE754 の乗算の結合が変わって 1 ulp の差が入る。この系はカオス的で忠実度を離散カウント（exact/near）で測るので、1 ulp が段0の「1ビットも動かない」判定を偽陽性にする。
2. **必ず inner loop の内側に置く。** 同一 `pi` 反復のうち `s.ElecFill += elecStep` / `s.SteamFill += ...` の更新は inner loop の**後**に来る。`EffectiveQty` は `s.ElecFill` を読むので、効率化材（`effNeed`）の決済と同じ位置（＝ElecFill 更新の後）に置くと、②が積んだ量と決済で再計算する量が**労働財だけ**ズレる。ズレは `GoodsBalance`（恒真式）も `MoneyConservation`（`ic` と `revenue` が同じ `pay` を共有）も捕まえない。
3. **π を「量」に掛ける**（`ReignitionOrderSettles * ReignitionOrderQty(...)`）。「代金だけに掛ける」と中間値（0.3/0.5）で「受け取っていない物への支払い」になる。量に掛ければ中間値が「発注の一部だけ約定させた」という意味を持つ。

**読む量（具体名）**：`s.Output`、`s.DesiredOutput`、`s.Inputs`、`Coefficients.ReignitionDemandFrac`、`EffectiveQty` 経由で `s.ElecFill` / `s.Mechanization` / `s.BuysLabor` / `inp.QtyPerOutput`、`clearPrice[inp.GoodId]`（③ で `m.Price` を捕捉した配列）、`ration[inp.GoodId]`。
**書く量（具体名）**：`inputCost[pi]`（scratch）、`revenue[inp.GoodId]`（scratch）。**この2本だけ**。

### 2.3 機構2（後退路）：発注の支払い能力ゲート

現行は「工場の投入需要だけが財布を見ない」という非対称がある（`popDemand` は `Min(desired, p.RemainingBudget / buyerPrice)`、軍需は `need * Min(1, budget/est)`、資本家建設は `Min(desiredGrowth/IndPerConstruction, budget/costPerUnit)` で切られる）。機構1は「発注＝買う約束」と宣言するので、約束できない者が発注できてしまうのは論理的な穴でもある。

```
if (coef.ReignitionOrderBudgetGate > 0)   // 既定0＝ゲートなし＝分岐に入らない
    oq = Math.Min(oq, coef.ReignitionOrderBudgetGate
                      * Math.Max(0, region.Pops[s.OwnerPopIndex].Savings) / Math.Max(Eps, clearPrice[inp.GoodId]));
```

段1で `LossFinanced` / `WorstLossRate` が悪化したときの後退路として用意する。既定は0（＝入れない）。**帯を確実に動かす**（貧国の死んだ工場が発注できなくなる＝連鎖断絶側）ので、必要になるまで点火しない。

### 2.4 計測器：`ordercheck`（物量↔貨幣の突合）

現行リポジトリに**物量と貨幣の対応を検査する不変条件は1本も存在しない**（`Invariants` の登録は `MoneyConservation` / `PopulationConservation` / `NonNegativeBounds` / `GoodsBalance` の4本のみ）。しかも `GoodsBalance` は ③ が `m.Stock = Max(0, available - sold)` と `m.LastSold = sold` を**同一の `sold`** から書くので**恒真式**である。したがって「発注が在庫を無償で食っていないか」を自動で捕まえる手段が現状ゼロで、`leakhunt`（`Simulation.ConservationProbe`）が追うのは貨幣側の保存量 D だけ。

**実装**：`EconomyStep.Scratch` に `PaidQty[ng]` を1本追加し、**すべての決済サイト**（投入・電力・蒸気・効率化材・再点火発注・投資束・国家建設・工場建設材料・軍需・pop消費・役務階層配分・義務教育の国庫買上）で `revenue[g] += pay` を書く隣に `paidQty[g] += qty` を書く。月末に `paidQty[g]` と `m.LastSold` の差を静的診断へ積み、`Simulation.ConservationProbe` と同型の **static bool（既定OFF・Runner コマンドで有効化）** で stderr へ財別に降順出力する。

- 物量を直接積む（`Σ revenue[g] / clearPrice[g]` と突合する方式にしない）。後者は商人カット・消費税・流通マージン・独占マークアップ・保険補助・輸出入の補正をすべて通す必要があり、補正の書き間違いが検出力を殺す。
- **この計器は現行コードでそのまま「幽霊の大きさ」を数値化する**（差が `Σ inputTrickle × ration` として出るはず）。段1の効果量の物差しになるので、機構より**先に**置く。

## 3. 確保すべき挙動 (a)〜(d) が満たされることの説明

### (a) 供給網が未整備でも上位（下流側）の工場を先に建てられる

`World.BuildFactory` → `ConstructionLeft` → `World.StepConstruction`（日次で労務費を払って進む）→ 完成で `BuiltScale += FactoryBuildScale` という経路に**一切触れない**。生産者オブジェクトは `Simulation` の生成時に役務・植民地財を除く全財ぶん存在するので、着工は既存オブジェクトに `ConstructionLeft` を立てるだけ。`BuiltScale > 0` は「④ 所得」ループの倒産条件（`s.BuiltScale <= Eps` を要求）から除外されるので**倒産免除**、かつ `floor = Min(Max(ScaleFloor, BuiltScale), ScaleMax)` で操業床が立つ。すべて不変。

### (b) その工場が動けないまま「材料不足」という需要を市場に出し続ける

**発注量の式（`Max(0, ReignitionDemandFrac × DesiredOutput − Output) × eq`）を1単位も変えない。** 変えるのは「代金を払うか」だけ。したがって (b) を運ぶ4経路がすべて数値同一で残る：

| 経路 | 読み手 | 本設計での変化 |
|---|---|---|
| 価格 | `MarketFlow.StepDay` の `eD = LastDemand × dev^(−ε)` と `TargetStock = TargetStockBuffer × LastDemand` | なし（`LastDemand` は不変） |
| 労働配分 | 「① 供給」ループ冒頭の `prodW[pi] = LastDemand × s.Scale` | なし |
| 数量による倒産再参入 | 「④ 所得」ループの `shortage = LastDemand > LastProduced + Stock` | なし |
| 国際市場 | `InternationalMarket` の `scale = Max(Max(LastDemand, LastProduced), TargetStock)`（事前 throttle パスと本パスの2箇所） | なし |

**さらに強化される点**：現在は上流が「物を取られて代金ゼロ」＝マージンを削られている。機構1では上流に**実際の売上が立つ**（`revenue[gi]` へ加算）。鶏卵問題が価格シグナルだけでなく実収入で解ける方向へ動く。

### (c) 生産していなくても下流財（＝投入財）の需要が立つ

発注の駆動量は `s.DesiredOutput`（＝`Capacity × profitFactor`＝作りたい量）であって `s.Output` ではない。「② 工場の投入需要」ループは `Bankrupt` を除外しないので、倒産機（「① 供給」ループ冒頭の `if (s.Bankrupt) { s.Output = 0; continue; }` で産出0）でも発注は立つ。**ここが「発注＝需要の表明」と「生産＝物理」の分離点そのもの**で、本設計はその量を保存する。

### (d) 物理的な正しさとの両立

- **買っていない物は消えない** → 在庫から出た `inputTrickle × ration` の全額に `clearPrice × 量` の代金が付く。現行の「代金の伴わない物量消滅」が構造的に閉じる。物を失った上流生産者は代金を受け取り、労働財を発注で買った工場は**実際に賃金を払う**（材料待ちの工場が工員を抱えているのは史実として正しい）。
- **無いものからは作れない（発注側）** → 発注は `s.Output` にも `produced[]` にも触れない。発注が産出を生む経路は存在しない。
- **★正直に書く未達点**：機構1は「消える物量に代金を付ける」であって「消える物量をゼロにする」ではない。市場から出た `(inputNeed + inputTrickle) × ration` のうち産出に体化されるのは `Output × eq × ration` だけで、発注ぶんは試運転・仕込み・スクラップとして消える（このエンジンには生産者の仕掛在庫という概念が一切なく、「買った投入はその期に消える」が既存の全経路の慣行）。現実の commissioning としては筋が通るが、完全な物量閉包ではない。**これを閉じる唯一の筋は §10-4 の資材置場（別ラウンド）。**
- **経16（当期在庫を見ずに前期充足率で産出が出る）は本設計では閉じない。** 作者裁定に従い「① 供給」ループには触れない。

## 4. 保存則・決定論・恒等性（既定0での証明手順）

### 4.1 財収支（`Invariants.GoodsBalance`）

検査式は `expected = m.PrevStock + m.LastProduced + m.LastImport − m.LastSold − m.LastExport`。③ は `m.Stock` と `m.LastSold` を**同一の `sold`** から、`m.LastProduced` を `produced[gi]` から書くので恒真式。**本設計は ③ に一行も触れない**（`coreDemand` の中身も `sold` の作り方も現行のまま）。機構1が触るのは「誰が払うか」だけ。→ 無条件・厳密に通る。

### 4.2 貨幣保存（`MoneyConservation`）

保存量は `BaseMoney = TotalMoney + Treasury − Loans` を基準にした「基礎貨幣 − 累積台帳（貿易/鋳造/不換発行）」。追加されるのは `ic += opay`（＝`inputCost[pi]`）と `revenue[inp.GoodId] += opay` の**同額の受払い1対**のみ。既存の投入決済と完全同型で、「④ 所得」ループの `valueAdded = producerRevenue − inputCost[pi]` を通って `rent` / `wages` → `Pops[...].Earned` へ流れる地域内の純移転。基礎貨幣に触れない。

赤字で所有者popの貯蓄が負に振れる経路も既存のもので受かる：`valueAdded < 0` → `wages = 0`・`privLoss = valueAdded × (1 − stateFrac)` → `rent = privLoss`（負）→ `Pops[s.OwnerPopIndex].Earned += rent` → `Simulation.BackstopNegativeSavings` が `Bank.Loans += 不足; Savings = 0` で受ける。したがって `NonNegativeBounds` の `Require(p.Savings)` を踏まない。税は `Math.Max(0, p.Earned)` を使うので負所得から貨幣は湧かない。

**★会計上の注意（設計の物語の訂正）**：「所有者が発注代を被る＝先に工場を建てれば金を失うのが正しい代価」という説明は、**本設計の看板ユースケース（プレイヤーが建てた工場）では成立しない**。「④ 所得」ループの `stateFrac = s.BuiltScale > Eps ? Min(1, s.BuiltScale / Max(s.Scale, Eps)) : 0` により、`BuiltScale > 0` の工場は `floor = BuiltScale` へ Scale が収束して `stateFrac → 1`＝赤字はほぼ全額 `region.StateSpent`（国庫の永続補助）へ行く。保存則は清潔だが、経済的な帰着先は国庫である。これを是とするかは §10-3 の裁定項目。

### 4.3 非負境界・人口保存

`NonNegativeBounds` が見るのは pop の `Savings` / `Size` / `Satisfaction` と market の `Price` / `Stock`。本設計はそのいずれにも新しい書き込みをしない。新しい割り算は機構2の1本のみで、分母に `Math.Max(Eps, ...)` を付す（0/0 → NaN、x/0 → Inf の混入経路なし）。人口には無関係。

### 4.4 決定論

RNG に触れない。`Dictionary` の列挙順に依存しない。`_scratch` は ThreadStatic で並列は試合単位なのでスレッド間共有なし。`PaidQty[ng]` を追加する場合は **`RentScratch` の確保分岐（`if (s.Produced.Length < ng)`）と `Array.Clear` 分岐の両方に必ず足す**。片方に落とすと IndexOutOfRange か、より悪く ThreadStatic 由来の**試合跨ぎの残留値＝実行順依存の非決定**になる（クラッシュしないので発見が遅れる種類の事故）。

### 4.5 既定0での恒等性の証明手順（段0で実際に踏む）

1. **静的**：新規コードは全て `if (coef.ReignitionOrderSettles > 0)` / `if (coef.ReignitionOrderBudgetGate > 0)` の内側にある。既定0では**分岐に入らない**＝実行されない。算術ブレンド（`(1−g)·A + g·B`）を使わない（`g` 側の被演算子が `0/0` や `Inf` を生むと `0.0 × NaN = NaN`、`Math.Min(x, NaN) = NaN`、`Math.Clamp` は NaN を素通しするので、ブレンド形は既定0でも壊れうる。既存の `CurrentInputFillGates` ブロックが `if (reqFull > Eps)` ガードを持っているのと同じ理由）。
2. **②のヘルパー化**：`Math.Max(0, coef.ReignitionDemandFrac * s.DesiredOutput - s.Output) * eq` を同じ式・同じ評価順のまま関数に切り出すだけ（`EffectiveQty` は純関数、`s.Output` / `s.DesiredOutput` は「① 供給」ループ以外で書かれない、`s.Mechanization` は ① より前に `region.Mechanization` から複製されて以降不変）→ 値はビット同一。
3. **動的**：段0の受け入れ条件は「`dotnet test` 180緑／`batch30` の exact・near・◎7割帯・固着・逸脱過多・破綻・デッドロック・異常・ハーネス不合格が**1つも動かない**／`leakhunt` 無言／`savetest` Q300 通過」。1つでも動いたら実装バグ（＝評価順を変えた、分岐の外に式を出した、Scratch の片分岐を落とした のいずれか）。

## 5. 新しい状態・新しい係数の全数

### 5.1 新しい永続状態（`Model.cs`）：**ゼロ**

## 7. 帯が動く方向の予測（★隠さず書く）

作者の方針は「リアリティ優先・帯とは切り分ける」（`ConstructionMaterialCarryover` の裁定の前例）だが、**動く方向の予測は必要**。段1（π=1）について、経路から導ける予測を符号付きで挙げる。

| # | 予測 | 経路 | 符号 |
|---|---|---|---|
| 1 | **当月の物量・価格は厳密に不変** | ③ に触れない。`MarketFlow.StepDay` は `LastDemand` / `LastProduced` / `LastImport` / `Stock` しか読まず `LastSold` を一度も読まない | ±0 |
| 2 | 上流（中間財・軍需上流）の `margin` ↑ → `SmoothedMargin` ↑ → 倒産 ↓ → `Scale` ↑ → 供給 ↑ → 上流価格 ↓ | 「④ 所得」ループの `revenue[gi]` 増 | **改善側**（死蔵財が減る） |
| 3 | 下流（発注した工場）の `valueAdded` ↓ → 所有者pop の貯蓄 ↓ → `IndInvestmentFrac` の投資原資 ↓ → 工業化速度 ↓ | `inputCost[pi]` 増 | **悪化側**（工業化の全球的な低下は exact/near を落としうる） |
| 4 | 中間財工場が多い国ほど強く効く＝**工業国が相対的に削られる** | 同上（工場数に比例） | ロンドン一強の**抑制方向**（覇権抑制の課題と同符号） |
| 5 | `LossFinanced` ↑ → `WorstLossRate > 0.35` の硬性異常判定に触れる恐れ | 倒産機は売上0のまま代金だけ払う。しかも `DesiredOutput` は倒産直前値で凍結（§10-2）＝**減衰しない** | **最大の落第リスク** |
| 6 | 労働pop の `Earned` ↑ → 家計購買力 ↑ → 翌月 `popDemand` ↑ → 消費財価格 ↑ | 労働財の発注に代金が付く | 弱い上昇圧 |
| 7 | **失業率は変わらない** | `LastSold` は不変。トリクルは**今日すでに** `LastSold` に乗っている。π は賃金を実体化するだけで、失業の過少計上そのものは解消しない | ±0（誤解しやすい点） |
| 8 | 国際市場は中立 | `scale = Max(Max(LastDemand, LastProduced), TargetStock)` の入力が不変 | ±0 |

**総合**：exact / near は動く。◎7割帯が改善か悪化かは事前に符号を決められない（予測2と予測3が逆向き）。**帯の劣化は較正で取り戻す対象であって、機構の可否の判断材料にしない。** ただし予測5（`WorstLossRate`）だけは硬性ゲートなので、触れた場合は §10-3 の裁定が要る。

## 8. `ReignitionTrickleConserves` と `CurrentInputFillGates` の処遇

### 8.1 `ReignitionTrickleConserves` → **点火せず、不要になって削除できる**

本設計と Conserves は**同じ場所の同じ量に対する逆向きの解**である。

- Conserves=1：トリクルを `coreDemand` から外して物量ごと捨てる → 在庫吸収・配給希釈・労働 `LastSold` 嵩上げが同時に消える → 実測の破局。
- 機構1：トリクルを `coreDemand` に残したまま、その物量に代金を付ける → 在庫吸収も配給希釈も `LastSold` も**そっくり残る** → 破局の原因が発生しない。

両者は共存できない（Conserves=1 だと物量が消えて π の対象が無くなり、π の決済だけが残って「在庫から引かれていない物への支払い」＝新しい不正になる）。したがって：

- **π が確定するまでは Conserves=0 のまま据え置く。**
- π=1 が確定した段階で、`coreDemand` の `(1.0 - coef.ReignitionTrickleConserves) * inputTrickle[gi]` を `inputTrickle[gi]` へ、`totalDemand` の `coef.ReignitionTrickleConserves * inputTrickle[gi]` を削除（既定0なのでビット恒等）。**作者の「再点火の検討をしないこと」という指示は守られる**（点火せず、削除されるだけ）。
- 削除でなくフィールドを残す選択もある（Runner の名前引きリフレクション・measure スクリプト・docs の参照を壊さない）。その場合はコメントを「**不読・`ReignitionOrderSettles` が上位互換として置換済み**」へ差し替え、実測の破局記録（ハーネス10/10・◎21→6・最貧国0.06）を新係数のコメントへ移設する。→ §10-6 の裁定。

### 8.2 `CurrentInputFillGates` → **恒久0のまま。不要にもならない。コメントを書き換えてはならない。**

これは「① 供給」ループの産出律速（経16＝当期在庫を見ずに前期充足率で産出が出る）の話で、②の需要（発注）とは触っている場所が別。本設計は産出側に一切触れないので、作者裁定の理由（「当期投入が涸れても産出できることが、上位工場を先に建ててから下流を整備するプレイの余地を作っている」）は**そのまま生き続ける**。

★**このコメントを「二重計上ゆえ誤り」等に書き換えないこと。** 「先月発注した材料で今月作るのだから当期在庫で再度律速するのは二重計上だ」という論法は、**仕掛在庫（買った材料を持つ場所）が実在するときにしか成立しない**。本設計は仕掛在庫を持たないので、この論法は使えない。書き換えると、後任が唯一の正しい修正経路（§10-4）を「モデル上の誤り」と信じて永久に封印する。

## 9. 却下した案と理由

### 9.1 段の分離（発注を効率化材と同じ「最劣後の残余段」に置く）

`effResid = Max(0, available − coreSold)` と同型に第3段を作り、コア → 効率化材 → 発注 の順で配給する案。**却下**。

③ の代数を追うと、`A = available`、`base = popDemand + inputNeed + investDemand + militaryDemand`、`T = inputTrickle` として：

- **`A ≤ base`（品薄）**：`coreSold = A`、残余ゼロ → `orderSold = 0`。`LastDemand` / `LastSold` / `LastProduced` / `Stock` のすべてが **`ReignitionTrickleConserves = 1` とビット同一**。
- **`A > base + effDemand`（だぶつき）**：発注は約定するが、この帯では現行の `ration` も既に1で誰も飢えていない。

つまり**代金も吸収も「余っている月」にしか働かず、幽霊が実際に仕事をしていた「足りない月」では Conserves=1 の完全再現になる**。実測の破局（最貧国・軍需上流）はまさに品薄セルで起きたのだから、この案の緩和力は定義上ゼロ。

### 9.2 発注幅の拡大（発注を `DesiredOutput` 満額にする＝意図発注）

**却下**。3つの独立した致命がある。

1. **失業が構造的にゼロへ潰れる**。工場の `Inputs` には必ず労働財が入り、労働は `Catalog.SpoilageOf` で 1.0（貯蔵不能＝`available = produced`）。満額発注で労働の `coreDemand` が `Σ Output×eq` から `Σ D×eq` へ跳ねると、需要が供給を超えた瞬間に `LastSold = LastProduced` → `unsold = 0` → `UnemploymentRate = 0` が恒等的に成立する。恐慌で失業が立たず、`Politics` の `UnemploymentMilitancy` が不発になり、社会保障・労組・社会主義の駆動源が消える。
2. **産出水位が潰れる**。定常で解くと `r_new = r_old²`（発注が `Output` でなく `D` に錨を打つため）。充足0.9の軽い逼迫でも産出−10%、0.7で−30%。`CurrentInputFillGates` がテスト6本を落としたのと同じ種類の故障を、供給側でなく需要側の分母から起こす。
3. **家計の押し出し**。工場の投入需要だけが財布を見ない非対称を全面展開するので、飢饉・封鎖ほど家計の取り分が機械的に削られる（醸造所が餓死しかけの pop を穀物で outbid する）。

**ただしこの案の「代金を払わせる」半分（π）は正しく、本設計の本体として採用した。**

### 9.3 資材置場（`Producer.InputStock` を持たせて自分の在庫で律速）

物理的には最も誠実だが、**本ラウンドでは却下**（§10-4 で将来の本命として残す）。現時点で判明している未解決点：

1. 発注を `Output + min(gap, rf×D)` にすると、**配給率を読まないため定常産出が `rf·r/(1−r)·D` に潰れる**（r=0.9 で現行の 1/3、r=0.8 で 1/7）。order-up-to（`Output + max(0, D − InputStock/eq)`）にすれば `Output* = r·D` で現行と一致するが、今度は倒産機が満額発注する副作用の封じ込めが要る。
2. 点火時の warm-start（既存工場の置場を満杯で初期化）は**全世界1ヶ月分の中間投入を代金も台帳記帳もなしに湧かせる**＝設計思想⑥の直接違反。`GoodsBalance` が恒真なので検査を通ってしまう。
3. 置場に `Spoilage` を適用すると、定常置場が `S* = (rf/spoil)·D·eq`＝**yardFill の恒久上限が `rf/spoil`**。小麦粉・麦（0.06）で 0.5、ジャガイモ・野菜（0.20）で 0.15、パン（0.25）で 0.12。**『パンの価格』というゲームで食料連鎖だけが恒久的に半減する。**
4. 置場は**市場台帳の外にある初の大規模な財ストック**で、`Inputs.Count` 変化時の破棄・州の帰属変更（分離独立の州物理移転）で無言の物量消滅が起きる。これを検査する不変条件が存在しない＝新しい抜け穴を掘ることになる。
5. `effFill = Min(LastInputFill, yardFill)` にすると置場が満杯でも市場の配給率で産出が切られる＝**緩衝在庫が緩衝にならない**。かといって `LastInputFill` を外すと較正の土台が動く。

### 9.4 建設中プラント専用の立ち上げ発注（本ラウンドの主線から外す）

着眼（真の鶏卵問題では投入価格が `mc` を押し上げて `profitFactor = 0` になり、`DesiredOutput = 0` ＝**現行のトリクルが1単位も立たない**）は正しく、本設計で唯一埋まっていない穴を突いている。しかし `ConstructionLeft > 0` を条件にすると：

- `World.BuildFactory` の呼び出し元は `PriceOfBread.App/ViewModels/GameViewModel.Production.cs`・`PriceOfBread.Runner/Program.cs`・`PriceOfBread.Tests/FranceTests.cs` の3箇所のみで、**SelfPlay（AI）は一度も呼ばない**（AI の産業動詞は `IndustryInvestFrac` → `StateBuildQueue` という財を指定できないマクロ経路）。
- したがって `batch30` の帯は1ビットも動かない＝**この機構だけがハーネスの外側にある**。回帰カバレッジゼロで新しい国庫支出・輸入需要（`InternationalMarket` の `scale` は `LastDemand` を読むので国内で最劣後にしても国外からは本物の財を引き寄せる）が入る。

→ §10-1 の裁定項目へ。

## 10. 未決（作者裁定が要る点）

### 10-1. 建設中プラント／冷えた設備の立ち上げ発注を入れるか

真の鶏卵問題（上流が存在せず投入価格が天井 → `mc` 巨大 → `profitFactor = 0` → `DesiredOutput = 0` → **発注が1単位も立たない**）は、本設計でも埋まっていない唯一の穴。埋めるなら3つの選択肢がある。

- (i) `ConstructionLeft > 0` 限定 → プレイヤー専用・帯が動かない・検証不能（§9.4）。
- (ii) 「冷えた設備」一般（`BuiltScale > Eps || Bankrupt || LastInputFill < 閾値`）へ広げる → **状態で発火するので AI＝プレイヤー完全対称**になり帯も動く（＝検証できる）。ただし影響が大きい。
- (iii) 入れない（現状の `profitFactor` ゲートを受容する）。

**裁定が要る。** 私の推奨は (ii) を段4で単独測定。理由＝設計思想⑤に照らして (i) は「プレイヤーだけが踏める物理法則」になり、しかも測れない。

### 10-2. 倒産機の `DesiredOutput` 凍結をどう扱うか（★π と同時に決める必要がある）

「① 供給」ループは `if (s.Bankrupt) { s.Output = 0; continue; }` を `s.Capacity` / `s.DesiredOutput` の代入**より前**に置いているため、**倒産中の `Capacity` と `DesiredOutput` は倒産直前の値で永久に凍結**し、トリクルは減衰も再計算もされず `0.03 × 過去の値 × eq` を出し続ける。

- π=0（現行）ではこれは無償なので害が見えにくい。**π=1 にすると、凍結された過大な `DesiredOutput` に対して実際に金が動く**（§7 の予測5）。
- しかし単純に毎月引き直すと、`mc = MarginalCost + InputCostPerUnit(s)` は現在価格ベースなので、**上流が高騰した月に `pf = 0` → 発注消滅**。倒産機の発注は「投入充足率を更新」ループのコメントが明言する「連鎖断絶と永続的脱工業化の防波堤」なので、これを一斉に消すのは危険。
- 選択肢：(a) 据え置き（現状）／(b) `DesiredOutput *= (1 − decay)` の緩やかな減衰（乖離だけ縮み、価格スパイクで信号が消えない）／(c) `Capacity` だけ毎月引き直し `profitFactor` は据え置き／(d) 完全再計算。

**裁定が要る。** 私の推奨は (b)。ただし π と同じバッチで点火せず、π の後に単独で測る。

### 10-3. `WorstLossRate` / `LossFinanced` が悪化した場合の処置

段1で SelfPlay の硬性異常判定（`ΔLossFinanced / 名目産出 > 0.35`）に触れた場合、(i) 機構を諦める／(ii) 機構2（支払い能力ゲート）を点火する／(iii) 閾値を較正で動かす／(iv) 10-2 を先に直す、のどれを採るか。関連して、**プレイヤーが建てた工場（`BuiltScale > 0`）の発注赤字は `stateFrac` 経由でほぼ全額国庫が負う**（§4.2）ことを是とするか（＝先行建設の代価が所有者に効かない）も同時に裁定が要る。所有者に負わせたい場合は、発注ぶんの `inputCost` を `stateFrac` の按分から除外する分岐が要る（保存は `StateSpent` と `Earned` の振り分けを変えるだけなので清潔に書ける）。

### 10-4. 資材置場（経16を閉じる本命）を将来ラウンドでやるか

「買った物が何にもならない」（§3(d) の未達点）と「無いものからは作れない」（経16）を**同時に**閉じる唯一の筋は、`Producer` に投入在庫を持たせ、①の律速を「市場の期首在庫」（`CurrentInputFillGates` がやって土台を下げた）ではなく「**自分が買って持っている在庫**」に置くこと。他社の在庫を当てにしないので産出の土台を一律に下げない。

やるなら §9.3 の5点（order-up-to 化・warm-start をゼロから始める・`Spoilage ≥ 0.06` の投入と貯蔵不能財を対象外にする・置場を含む物量の閉包を検査する不変条件を先に新設する・`effFill` の合成を Min でなく置換にする）を設計に織り込むこと。**別ラウンドの大きい課題。**

### 10-5. π の刻み方

0/1 のみで扱うか、中間値（0.3 / 0.5）で刻んで較正の途中値として使うか。式は量に線形に掛かるので中間値は意味を持つ。

### 10-6. `ReignitionTrickleConserves` を削除するか、コメント化して残すか

削除は Runner の名前引きリフレクション（`GetField(flag) ?? throw 係数が見つからない`）・measure スクリプト・docs の参照を同一コミットで掃除する必要がある。残す場合はフィールドを不読にしてコメントを差し替える。

### 10-7. `LastShortage` の扱い（付随・独立に処理可）

`m.LastShortage = Math.Max(0, totalDemand − available)` は**書かれるだけで読み手が1つも存在しない**（SimCore 全 `.cs` の grep で代入と各所のゼロ化のみ）。③のコメントは「価格シグナル（LastDemand/LastShortage）」と書いているが、実際に効いているのは `LastDemand` だけ。死んだテレメトリとして削除するか、UI 診断へ配線するか。本設計とは独立。
