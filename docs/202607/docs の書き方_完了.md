# docs の書き方（★これは執筆者向け。実装側は読まない）

## 方針（2026-07-29 作者裁定）

> 「作業ファイルに全ての指示を詰め込むのではなく、**機能ごとに docs を用意した方がミスが少ない**ことが判明した。
>   つまり**機能ごとに独立した docs を作成。それらは HANDOFF 含め他文書に依存しない。**」

| | |
|---|---|
| **1機能＝1ファイル** | 巨大な作業リストに詰め込まない |
| **完全に自己完結** | `HANDOFF.md` にも他の docs にも依存しない。**それ1つで実装に着手できる** |
| **ファイル名** | `YYYYMMDD_機能名.md`。★**通し番号は付けない**（索引や順序を示唆してしまうため） |
| **`old/`** | **既に実装済み**（実装本体はこのPCに無い）。★**新しい docs から参照しない** |

★ **重複は許容する。** §0 の前提ブロックは全 docs に同じものが入る。
これは冗長ではなく**標準ヘッダ**であり、独立性の対価として意図的に払う。

# 0. 前提（本書だけで読める形にした）

⚠ **`HANDOFF.md` も他の docs も参照しないこと**（最新でない）。以下は現物のコードから取った恒久の前提で、
本書はこれだけで実装に着手できる形にしてある。

## 0-1. 環境

| | |
|---|---|
| **GUI起動禁止** | 会社PCのため。許可は headless のみ（build / test / Runner CLI / grep） |
| **実装は別ブランチ** | この環境ではコードを変更しない。成果物はドキュメント |

## 0-2. 設計思想7則（違反した変更は差し戻される）

| # | 規律 | 意味 |
|---|---|---|
| ① | **台本禁止** | 暦年ハードコードもスクリプトイベントも置かない。「1848年に革命を起こす」とは書かず、条件だけを書く |
| ② | **外科的倍率・国別特例の禁止** | 国ごとの「データ」（初期識字率・資源賦存）はよい。国ごとの「倍率」（英だけ生産性1.3倍）はだめ |
| ③ | **休眠フラグ規律** | 新機構は既定0で入れ、**既存と1ビットも変わらないことを証明してから**点火する |
| ④ | **帯を壊さない** | 史実忠実度の分布が最優先。機構が史実的に正しくても帯を壊すなら差し戻す |
| ⑤ | **プレイヤーとAIは完全対等** | プレイヤーだけが使える機構を作らない |
| ⑥ | **決定論・保存則** | 同じシードは必ずビット単位で同じ結果。貨幣と人口は湧かず消えず、移転のみ |
| ⑦ | **UI恒久規律** | 画面に説明文を書かない。数値・名前・状態などのデータだけを置く |

★ ⑥は運用上とくに重い。**浮動小数は非結合的**なので、項を足すときは**掛け算の順序を保存**しなければならない。
係数を0にしたまま `Math.Clamp` で包んだだけでも軌道が動く。

## 0-3. UI恒久規律（⑦の細目・全セッションで厳守）

1. **ゲーム中にテキストで説明を書かない。** UIに置いてよいのは数値・名前・状態などの**データだけ**
   （★**データを並べるツールチップはOK**・「〜すると〜になる」等の説明文・注釈・かっこ書きの補足はNG）
2. **漢字1字の略称を絶対に使わない**（例：緊+ →「緊張を増加」／計 →「合計」）
3. ホバー/ツールチップの題も**指標名のみ**（「GDP（年次・財ティア別）」のような（）注釈を付けない）
4. バー（スライダー）は**常に0〜100%を全幅**とし、上限/下限があるときは thumb がそこで止まる（バー自体を短くしない）

## 0-4. 判定基準

| | |
|---|---|
| **現在の方針** | **機能実装を優先。バランスは後回し** |
| **合格条件** | **破綻 0/30 ・ デッドロック 0/30 ・ クラッシュなし** のみ |
| **帯（後回し）** | 30シード・**1914年12月（Q524）の断面**で各国の政体と主要6法を史実と突合。`exact` は完全一致、`near` は近い政体まで許容 |
| **1915年以降** | **自由歴史**。参照表を作らない（`Coefficients.cs:1094`） |

★ 参照表は**答え合わせにしか使われない**。シミュレーションはそれを一切読まない。

⚠ **恒等の物差しは現在無効。** 厳密恒等を証明する必要が出たら、
**その時点で `chronicle 1` を取り直してから**着手すること。

## 0-5. 記録の作法

★ **記録は係数の行内コメントが担っている。** したがって**係数を生まない作業（リファクタ・配線・UI）は記録先が無い。**
本書のような設計docに、着手・見送りを明示的に書くこと。

# §1 以降の構成（推奨）

`20260729_金利と通貨レジーム.PARTIAL.md` が実例。

| 節 | 内容 |
|---|---|
| **1. 問題提起と判断基準** | ★**作者の発言をそのまま引用**する。何を解こうとしているかが実装側に伝わる |
| **2. 診断** | ★**なぜ今そうなっていないか**を file:line と手計算で。推測を書かない |
| **3. 設計** | 何をどう変えるか |
| **4. 実施順** | ★**1項目1バッチ**。各行に「触る場所 / 挙動 / 帯リスク」。**帯リスクなしのものを先頭に置く** |
| **5. 却下すべき案** | ★**やらないことを書く**。理由は計算で示す。これが無いと同じ案が再提案される |
| **6. 残る未決** | 判断が要るものを明示 |

## 書くときの規律

| | |
|---|---|
| **推測を書かない** | 主張は必ず `file:line` と実際に読んだ内容で裏づける。確認できなければ「**未確認**」と明記 |
| **存在しない実装に行番号を付けない** | 新機能は「設計」として書き、`file:line` を捏造しない |
| **数値は計算過程を示す** | 「約2倍」ではなく、式と代入値を書く |
| **却下は計算で潰す** | 「複雑になる」ではなく「θ=0.65 では −2.4% にしかならない」と書く |
| **撤去するものを明記** | 足すものだけでなく、**消えるもの**を列挙する |

# 索引を持たない

★ 各 doc が自己完結なので、**索引ファイルは作らない**。
作ると「索引が古い」という新しい失敗が生まれる（`HANDOFF.md` と `00_作業リスト.md` で実際に起きた）。

**ファイル名の日付が新しさを示し、機能名が中身を示す。それで足りる。**
