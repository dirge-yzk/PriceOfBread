## 1. batch30 高速化（#29）★実測で決着

### 1-1. 結論：GCは効かない。並列度だけが効く。

`docs/202607/20260727_batch30高速化_部分完了.md` の見立ては**本機では逆だった**。同書は「実行を伴う計測を一切していない」静的見積りで、しかも32コア機を前提にしていた。

| 条件 | n | par | 所要 | 1シード当たり |
|---|---|---|---|---|
| R1 素（Workstation GC） | 6 | 6 | 546秒 | **91.0秒** |
| R2 `DOTNET_GCgen0size=10000000`（256MiB） | 6 | 6 | 557秒 | 92.8秒（**−2%＝悪化**） |
| R3 ServerGC+DATAS0+非並行GC | 6 | 6 | 521秒 | 86.8秒（+4.6%＝ノイズ幅） |
| R4 **par=8 素** | 8 | 8 | 613秒 | 76.6秒（+18.8%） |
| R5 par=8 + ServerGC一式 + Heap8 | 8 | 8 | 627秒 | 78.4秒（**R4より悪化**） |
| R6 par=12 素 | 12 | 12 | 802秒 | 66.8秒（+36%） |
| **R7 par=16 素（論理コア数）** | 16 | 16 | 981秒 | **61.3秒（+48%）** |

- **段0（gen0size）と段1-1（Server GC）は不採用。** 実測で効果なし〜逆効果。同書の「①と②は分離できない／Server GC 無しで par を上げると回帰する」は本機では成立せず、**素の Workstation GC のまま par を上げるのが最速**。
- 同書の「30÷6=5波→1波＝**4〜5倍**」は物理32コア前提の式。本機の実測は **1.48倍**。
- 物理8コアでも**SMTが素直に伸びた**（par=8→16 で更に+25%）。「物理コア数で頭打ち」という予想も外れ。

### 1-2. 適用した変更

**`SelfPlay.cs` RunBatch の既定並列度**
```
旧: Math.Clamp(Environment.ProcessorCount / 2, 2, 6)
新: Math.Clamp(Environment.ProcessorCount, 2, Math.Max(2, n))
```
旧上限6の根拠（`SelfPlay.cs:721-722` のコメント）は **2026-07-03 時点の Telemetry 常時ON**（TurnSnapshot が四半期に比例して増える）に由来し、**2026-07-09 の常時OFF化で前提が失効**したまま一度も見直されていなかった。`n` でクランプするのは 30シードに32ワーカーが純粋な遊休になるため。

**batch30 の所要：48分26秒（par=6）→ 約33分（par=16）**

**恒等性は実測で確認済み**：`selfplay-batch 8 - 4`（2波）と `selfplay-batch 8 - 8`（1波）の出力が**バイト単位で完全一致**。並列度は結果に影響しない。

### 1-3. 併せて入れた防御（いずれもビット恒等）

1. **OOMを握り潰さない**（`SelfPlay.cs` の `catch (Exception ex)` の直前に `catch (OutOfMemoryException) { throw; }`）
   従来は OOM も全捕捉に落ち、その試合が `Completed=false`＝**「破綻(未完走)」として静かに帯を汚染**していた。しかもどのシードが先にメモリ上限へ当たるかはスレッドの到達順次第で**run ごとに変わり再現しない**。空きRAM 4GBの本機では実在のリスク。
2. **`WorldData.Nations()` のプリウォーム**（`Parallel.For` の直前）
   `WorldData.LoadDoc`/`Nations` は `lock` も `Lazy<T>` も無い check-then-act。生成値はどの経路でも同一なので無害だが、並列度を上げるほど窓が広がる。恒久対策は `Lazy<T>(ExecutionAndPublication)` 化。
3. **`MultiNationSim.cs:65` の `Resources = cres` を `[.. cres]` へ**
   すぐ下の `:80` は複製済みで「Resourcesは試合ごとに複製（キャッシュ共有回避）」とコメントしている＝作者は危険を認識済みで1箇所だけ漏れていた。

## 3. 点火した機能の実効確認 — 4件が狙いを外していた

「配線済み＝点火すれば効く」は成り立たなかった。**機能優先の方針下では「点火したのに効いていない」は最優先の修正対象**。

### 3-1. `SingleNationTradeParity` は本番経路に一切載らない【要注意】
`Trade.Step` は先頭 `Trade.cs:13` の `if (!w.TradeEnabled) return;` で即リターン。`TradeEnabled=true` を立てるのは **`PriceOfBread.Tests/TradeTests.cs:12` と `ExportRevenueTests.cs:25,70` のユニットテスト2本だけ**（`Scenario.cs:58` 既定false・`NationConfig.ToScenario` も `MultiNationSim` の分離建国も未設定）。batch30・較正・GUI はすべて `InternationalMarket` 経由。

→ **1.0 のまま維持**（単一国モードを多国版へ寄せる作業自体は達成・169テスト緑）。ただし **batch30 では測定不能**であり、「第2群6件を測定した」と書いてはならない。Coefficients.cs の行内コメントに明記済み。

### 3-2. `MintWageShare` はゴールドラッシュの当事国で不発【是正せず・理由あり】
アメリカは `world.json:524` で `farmLordShare=0` のため RGO 生産者の `LaborPopIndex == OwnerPopIndex` となり、`Simulation.cs:1691` の条件を満たさず **mintWage=0＝厳密に恒等**。

→ **そのままにした。** カリフォルニアの49ersは実際に**自営の採掘権保有者**で賃金労働者ではなく、自営なら鋳造代金が全額本人に入るのは正しい挙動。この機構が効くのは地主階級を持つ国（スペイン領鉱山・ロシアの金鉱）で、そちらの方が史実に合う。
**作業リストの「掘り子の高賃金＝ゴールドラッシュの創発」という説明が実態と合っていない**、というのが正しい整理。直すなら `world.json` のアメリカの `farmLordShare` を触ることになるが、米国の農業構造全体を変える改変で副作用が大きすぎる。

### 3-3. `TariffInterestPrefWeight` の希釈【是正した】
読み値 `Region.TariffInterest` を書くのは `Politics.cs:1086` の `CheckSecession` 内だけで、
- `Politics.cs:1074` `if (w.Regions.Count < 2) return;` ＝**単州国は永久に0**
- `Politics.cs:1085` `r.Id == 0` を skip ＝**首都州は永久に既定0**（首都は離脱しないため）

ところが `PolicyPreferences.cs:116` は首都を含む全 active 州で平均していた＝**構造的なゼロが必ず分子に混ざり、州数の少ない国ほど強く希釈**（2州国なら実効半減）。

→ 平均から `Id == 0` を除外。**非恒等なのでバッチが要る**（第3群と同時に測定中）。

### 3-4. `CrimePushWeight` がノイズ級だった【0.3 → 6.0 へ再点火】
`crimeRate` の上限は `CrimeBase 0.01 × (1 + CrimeUrbanWeight 0.6) = 0.016`（`Crime.cs:37`）。
0.3 では押し出し上限が **0.0048**＝同じ式の `PushUnrestWeight`（上限0.5）の**約1/100**。`Territory.cs:97-98` のコメント自身が旧経路を「約0.3%とノイズ級」と書いており、0.3 では同じ桁のまま＝**配線しただけで機構が死んでいた**。

→ **6.0** で上限 0.096＝不満項の約2割＝副次要因として意味を持つ水準へ。

### 3-5. `StateSpendTreasuryClamp` は実質ブール【記録のみ】
`Simulation.cs:1642` は `<= 0` の判定にしか使っておらず、**係数の大きさが式に一切現れない**（返り値は `Clamp(Max(0,Treasury)/planned, 0, 1)`）。1.0 と 0.3 は同一挙動。「連続の強度」を意図しているなら実装が追随していない。

### 3-6. 値の妥当性で要監視（未対応）
- **`ExternalPressureDerived=1.0` が15件中で最も軌道への影響が大きい。** `TechLevel` は `World.cs:69` で0開始のため**開始直後は全国 ExternalPressure≈0**＝従来の定数0.3による改革派×1.15 の追い風が**フランス革命期に消える**。後期は逆に後発国が最大1.0（従来の3.3倍）。単独バッチへの分離が望ましい。
- **`TransportCongestionWeight=1.0`**：序盤は実効容量が `TransportBaseline=50÷州数` しか無く、律速率がほぼ全交易州で0近傍＝**乗数が事実上ほぼ全国で2.0に張り付く**可能性（実測未確認）。設計意図「交易集約国だけ増強」と逆の一律2倍になっていないか、0.3〜0.5 との比較が要る。
- **`MigrantDowryWorldBase=1.0`**：基準の単位が揃っていない。旧基準は受入 pop（農民/労働者）の1人当たり貯蓄だが、世界平均は貴族・資本家を含む**全pop平均**。持参金＝外生マネーの総量を押し上げる方向。0.5 等の中間値が安全。

## 4. 段3-2（`EconomyStep` スクラッチ化）の実装仕様 — 監査済み・未実装

**総合判定＝原理的に安全。** 19本すべて Run 外へ参照が漏れず、`ng`/`np`/`npops` は Region 生成後に不変（`Producers.Add` は `Simulation` コンストラクタ内のみ・Pops の増減ゼロ）、**同一 Region への並行 Run は発生しない**（`Parallel` は `SelfPlay.cs` のシード単位と `Calibration.cs:44` のセル単位だけ。`MultiNationSim.cs:313` の国ループも `Simulation.cs:1149` の州ループも逐次 `foreach`）。

削減量＝**約163GB／全体約173GBの94%**（呼び出し 604×3×158×30 ＝ 8,588,880回・約20KB/回）。

### ★実装の必須条件（1つでも欠けると非恒等）
1. **スクラッチは `Region` に持たせる。** `Coefficients`・`static`・`[ThreadStatic]` はいずれも不可（`Calibration.cs:52` が `Coefficients` 1個を複数スレッドで共有しているため／`[ThreadStatic]` は「長さ以上なら流用」を誘発し 2 と衝突）。
2. **長さは `ng`/`np`/`npops` と厳密一致。** `if (buf is null || buf.Length != ng) buf = new double[ng];` の形。`EconomyStep.cs:179` が `isStaple.Length` を、`:555` が `isService.Length` を実際に読み、後者は `elecOn` の判定に直結する＝**オーバーサイズ流用は非恒等**。
3. **Run 入口で18本を `Array.Clear`。`effChosen` だけは既存の −1 埋め（`:562`）をそのまま残す**（0埋めに置き換えると非恒等）。
4. `conCarryApplied` は 3 の一律クリアに含めれば `:936` の `?? 0` と数値的に一致する（null をフラグとして読んでいるため。遅延クリア・`??=` 温存は非恒等）。

### ★敵対的検証が3レンズ全員一致で指摘した罠
初回監査は「`+=` 累算器は ng長7本」と列挙したが、**`producerCount`（`EconomyStep.cs:32`／`:566` の `++`）が8本目**で漏れていた。読み手は `:1230`（`== 0` で continue）・**`:1242` の `1.0 / producerCount[gi]`（除数そのもの）**・`:1325`・`:1335`。クリアし忘れると k 回目の呼び出しで `producerCount[gi] = k×n` となり **Σshare = 1/k < 1 ＝ revenue の (1−1/k) が誰にも渡らず消滅＝貨幣保存の破壊**。
→ **7本ではなく19本を一律クリアすること。**

### 使い回し対象外（Region の月跨ぎ状態）
`region.ColonialImportPipeline`（:72）／`region.ConstructionCarryover`（:346）／`region.EffFirms`（:1321）。
`:1321` は既に「null か長さ不一致なら再確保」という**まさに今回推奨したいパターンの既存前例**。

## 8. ★2026-07-28 の測定汚染事故（方法論の教訓・再発防止済み）

### 何が起きたか
巨大建造物の段2（同定キーの `Id` 一本化）は**挙動不変のリファクタ**として実装したが、batch10 の結果が **167行**食い違った（勝者分布・恐慌回数・分離独立数・政体分布まで全面的に別物）。

**真因＝別セッションが同じ作業ツリーを並行して編集していた。** 設計書作成側に「実装はしない」と指示していたにもかかわらず7箇所を編集していた（`world.json` でロシアを黒海へ／`Simulation.cs` の水力 `TechOnset` 9.9→1.3／缶詰の技術ゲート／電力の燃料シェア／`Geo.cs` のカラカス座標／`FactionSnapshot.cs` 2件）。
**私のビルド（11:52）はこれらを取り込んでおり、観測した差分は段2の効果ではなくそれらの効果だった。** 12:02-12:03 に相手が巻き戻したため、12:38 の二分探索では「自分の3点を戻したら一致した」ように見えたが、実際には**相手の編集が消えていただけ**＝二分探索は最初から動く標的を測っていた。

### 私の失敗＝疑う順序を間違えた
**実測が推論と矛盾したとき、まず疑うべきは測定の有効性だった。** 「ガード・ログ・未参照係数の削除はいずれも変化を起こしえない」という推論は最初から正しかったのに、実測が矛盾したので**推論の方を約1時間疑い続けた**。あやうく「未参照フィールドの削除で軌道が動く」という誤った結論を文書に残すところだった。

**再現性の確認だけでは不十分。** 同一バイナリの再実行が一致することは確認したが、それが保証するのは「同じバイナリなら同じ結果」だけで、「**そのバイナリが自分の意図したソースから作られたか**」は別問題である。

### 再発防止＝`measure.sh`（プロジェクト直下・実装済み）
検出ではなく**免疫**にした。
```

```
