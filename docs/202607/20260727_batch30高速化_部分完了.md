**恒等性は実測済み**：`selfplay-batch 8 - 4`（2波）と `selfplay-batch 8 - 8`（1波）の出力が**バイト単位で完全一致**＝並列度は結果に影響しない。

### 2026-07-27 実施済み（すべてビット恒等）
1. **既定並列度** `SelfPlay.cs`：`Math.Clamp(ProcessorCount/2, 2, 6)` → **`Math.Clamp(ProcessorCount, 2, Math.Max(2, n))`**。旧上限6の根拠（`SelfPlay.cs:721-722`）は 2026-07-03 の Telemetry 常時ON時代のもので、**07-09 の常時OFF化で前提が失効したまま一度も見直されていなかった**（本書 §1-4 の指摘どおり）。
2. **OOM を握り潰さない**（本書の最重要指摘）＝`catch (Exception ex)` の直前に `catch (OutOfMemoryException) { throw; }`。
3. **`WorldData.Nations()` のプリウォーム**（本書 §2-1）＝`Parallel.For` の直前。
4. **`MultiNationSim.cs:65` の `Resources = cres` → `[.. cres]`**（本書 §2-2 の複製漏れ）。

### 本機での残り優先順位
1. **そもそも回す本数を減らす**：崩壊判定（破綻/デッドロック/異常）はシード独立なので30本不要。`selfplay-batch 10` で**コード変更ゼロ・リスクゼロで約1/3**。帯（exact/near）を測る回だけ30本に戻す。**現時点で最も確実な短縮。**

## 結論（先に）※以下は32コア機の前提。本機は上の追記を参照

**遅い主因は設定2つで、どちらもコードの計算内容に触れない。**

| # | 何が | 現状 | あるべき | 見込み |
|---|---|---|---|---|
| 1 | `SelfPlay.cs:723` の並列度 | **上限6でクランプ**（32コアでも6） | `min(コア数−2, n)` | 30÷6=5波 → 1波＝**4〜5倍** |
| 2 | GC | **Workstation GC**（ヒープ1本） | Server GC + DATAS無効 | **10〜50%** |

**ただし①と②は分離できない。** Workstation GC のまま並列度だけ上げると、2026-07-08 に実際に起きた回帰（`HANDOFF.md:561` の par=10 で 21分→28分）を再現する。

## ★最重要の落とし穴：OOM が静かに帯を汚染する

`SelfPlay.cs:684` は `catch (Exception ex)` の全捕捉で、**`OutOfMemoryException` もここに落ちる**。その試合は `Completed=false` ・勝者「(中断)」の `MatchResult` になり、そのまま `BatchSummary` の **`破綻 k/30`** に混入する。

つまり並列度を上げすぎたときの症状は「プロセスが落ちる」ではなく **「実装バグに見える静かな破綻レコード」** である。さらに悪いことに、6本のうちどのシードが先にメモリ上限へ当たるかは**スレッドのアロケーション到達タイミング次第**なので、**`BatchSummary` が run ごとに変わる＝再現しなくなる。**

**→ 並列度を上げる前に、OOM を握り潰さず即座に落とすようにすること。**
```csharp
catch (OutOfMemoryException) { throw; }   // ← 既存の catch (Exception ex) の前に置く
catch (Exception ex) { /* 既存 */ }
```
これを入れずに par を上げると、帯が壊れたのか OOM なのか区別できなくなる。

## 段0：ビルド不要でGCが主犯かを切り分ける（最初にやる）

別セッションのビルドを妨げず、**今日そのまま測れる唯一の実験**。環境変数だけ。

```bash
DOTNET_GCgen0size=10000000 dotnet run -c Release --project PriceOfBread.Runner -- selfplay-batch 30
```

`DOTNET_GCgen0size` は **16進バイト数**（`10000000` = 256MiB、`4000000` = 64MiB）。runtimeconfig に等価キーは無く env 専用。

- **縮むなら** GC が主犯 → 段1へ進む価値が確定する
- **縮まないなら** GC は主犯でない → Server GC の投資を見送り、並列度だけ上げればよい

## 段1：ビット恒等・即効（検証済み）

### 1-1. Server GC（`PriceOfBread.Runner.csproj` の PropertyGroup）
```xml
<ServerGarbageCollection>true</ServerGarbageCollection>
<ConcurrentGarbageCollection>false</ConcurrentGarbageCollection>
<GarbageCollectionAdaptationMode>0</GarbageCollectionAdaptationMode>
```

**★3行目を省くと効かない。** .NET 9/10 では Server GC を入れると **DATAS（Dynamic Adaptation To Application Sizes）が既定でON**になり、ヒープ数を1から徐々に増やす制御が入る。「Server GC にしたのに速くならない」の典型原因がこれ。

`ConcurrentGarbageCollection=false` はバッチ＝スループット優先（背景GCスレッドにコアを取られない）。ポーズ時間は無関係なので切ってよい。

### 1-2. ヒープ数を「コア数」でなく「実並列度」に合わせる
Server GC の既定ヒープ数は**論理コア数**。並列度6のまま入れると32ヒープが空回りする。`HeapCount` に MSBuild プロパティは無いので `runtimeconfig.template.json` を Runner に新設：

```json
{ "configProperties": { "System.GC.HeapCount": 30 } }
```

env で試すなら `DOTNET_GCHeapCount` は **16進**（30が欲しければ `1E`。`30` と書くと 0x30=48ヒープになる）。DATAS=0 とセットで指定すること（DATAS がONだと HeapCount は上限としてしか効かない）。

### 1-3. 並列度の上限を外す（`SelfPlay.cs:723`）
```csharp
MaxDegreeOfParallelism = parallel ?? Math.Clamp(Environment.ProcessorCount - 2, 1, Math.Max(1, n))
```

**★ `Math.Clamp(x, 2, n)` は n=1 のとき min>max で例外**（元の提案どおりに書くと単発実行で落ちる）。上を使うこと。`n` でクランプするのが要点で、n=30 に対し32ワーカーは純粋な遊休。これで `Calibration.cs:43` の `Math.Max(2, ProcessorCount - 2)` と規約も揃う。

**推奨値**：32コア/32GB → `30`／16コア/16GB → `12`（Server GC + HeapCount=8。Workstation GC のままなら `8` で止める）。

### 1-4. 上限6の根拠は失効している
`SelfPlay.cs:721-722` のコメントの前提は**2026-07-03時点**のもの。当時生きていた Telemetry（`TurnSnapshot` 208B × 604四半期 × 53国 ＝ 7〜13MB/試合で四半期に比例して増える）と `Diplomacy.Log` は、**翌週2026-07-09に常時OFF化された**（`SelfPlay.cs:566-567`）。以後この上限は一度も見直されていない。

オブジェクトグラフからの静的積算では **live 約15MB/試合**（財136・州158・国53・植民地46）で、30並列でも live 0.5GB 級。`MatchResult` は `World`/`Simulation` への参照を持たないので完了試合は即回収される。四半期に比例して伸びる構造は他に残っていない（`EndedWars` は256件リング、`Parties` は上限13、`World.Explain` は既定null）。

> ⚠ ただし検証エージェントは「15MB という積算は静的読解では裏取り不能」として**判定不能**にしている。ピークRSSは live でなく GC のヒープ予算で決まるため、実測が要る。

## 段2：並列度を上げるなら入れておく防御（ビット恒等・速度目的ではない）

### 2-1. `WorldData` の遅延初期化がスレッド非安全
`WorldData.cs:79-88`（`LoadDoc`）と `:90-97`（`Nations`）は `if (_x is not null) return _x; _x = 生成; return _x;` の check-then-act で、**lock も `Lazy<T>` も volatile も無い**（SimCore 全体で `lock` は `SaveGame.cs:48` の1箇所のみ）。`SelfPlay.cs:559` が `Parallel.For` の本体からこれを呼ぶ。

現状は無害（生成される値がどの経路でも同一・x64 はストア順序を保つ）だが、**並列度を上げるほど窓が広がる本物の race**。

```csharp
// SelfPlay.cs:724 の Parallel.For 直前
_ = WorldData.Nations(); _ = Catalog.Goods.Length;   // プリウォーム
```
恒久対策は `static readonly` 化か `Lazy<T>(LazyThreadSafetyMode.ExecutionAndPublication)`。

### 2-2. `MultiNationSim.cs:65` が複製を1箇所だけ取りこぼしている
`Resources = cres` が共有キャッシュの `int[]` を複製せず `Colony.Resources`（mutable な public フィールド）へ入れている。**すぐ下の `:80` は `Resources = [.. c.Resources]` と明示複製し「Resourcesは試合ごとに複製（キャッシュ共有回避）」とコメントしている**＝作者は危険を認識済みで1箇所だけ漏れている。同型が `Simulation.cs:650` にもある。

現状は書き込む者がいないのでバグではないが、鉱物枯渇や資源発見が `Resources` 配列自体を書き換える実装に将来触れた瞬間、並列度に比例して発現する非決定バグになる。`int[]` のコピーだけで浮動小数に触れない。

## 段3：条件付き（検証に通った項だけ採用）

### 3-1. 最大の熱源＝`MarketFlow.StepDay`（`MarketFlow.cs:14-98`）
日次×全州×全財のループで、1財あたり `Pow`×5 / `Log`×3 / `Exp`×1。係数の実値（`PriceElasticity=0.5`・`PriceAmpPower=3.0`・`SoftBandSharpness=8.0`）はいずれも初等演算へ分解できる形：

`Pow(x,0.5)`→`Sqrt(x)`／`Pow(x,3.0)`→`x*x*x`／`Pow(|t|,8.0)`→`t2=t*t; t4=t2*t2; t4*t4`

**★ただし分解版は丸めが複数回入るため一般に最終ビットが変わる。1 ulp のズレでも604四半期の非線形力学で軌道が発散し、帯が壊れる。** 採用前に、置換前後がビット一致するかを実走の値域で全数検証すること（`leakhunt` と同型の使い捨てハーネスで実値を dump し `BitConverter.DoubleToInt64Bits` で比較）。**検証を省いた一括置換は禁止。**

### 3-2. `EconomyStep.Run` が入口で毎回23本の作業配列を new
約20KB/呼び出し・バッチ合計で約169GB のアロケーション。`Region` にスクラッチ型を持たせて再利用する。ただし検証で**恒等でない可能性が1点**指摘されている：`conCarryApplied`（`EconomyStep.cs:309`）は `double[]? = null` で宣言され `:936` で **null をフラグとして読む**ため、使い回すと意味が変わる。この1本だけは毎回 null 化が要る。

### 3-3. その他（検証済み・恒等）
- `MarketFlow.cs:17-20` の財ループが Tier ソート順で `Market[]` へランダムアクセスしている → Id 昇順走査へ（走査順は結果に無関係と確認済み。`Model.cs:348` に Id 直引きの既存機構あり）
- `World.StepConstruction` が建設中でない生産者を毎日全走査（2.0e9回の空振り分岐）
- `SoftBand`（`MarketFlow.cs:92`）が定数の `Math.Log` を毎回計算。**ただしキャッシュ先を `Coefficients` にすると `Calibration.cs:52` が1インスタンスを72セルへ共有しているため多スレッドから書かれる**＝保持場所に注意
