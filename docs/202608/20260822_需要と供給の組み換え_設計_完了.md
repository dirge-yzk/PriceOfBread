## 1. 診断の確定 ― 「需要が計算できていない」は**不正確**

需要は計算されている。`EconomyStep.cs:1239` の5項（pop消費・工場投入・建設投資・軍需・再点火トリクル）＋`:1259` の効率化材は、どれも真面目に積まれている。壊れているのは**計算**ではなく**配線**である。

### より正確な言い方（3つの独立した事実）

**(A) 需要「量」が、価格を経由せずに、直接、労働の配分器として使われている。**
`EconomyStep.cs:300`
```csharp
prodW[pi] = region.Markets[s.GoodId].LastDemand * s.Scale;
```
`prodW` の読み手は `:306`（プール総和）と `:385`（シェア）の2箇所だけ（全域grep確認）。`fraction` は `:463` で `s.Capacity` にしか入らない。つまり **`LastDemand` は「価格を作る」仕事のほかに「労働を配る」という第二の仕事を直接やっている**。しかも `totalDemand` は全項が物量（`:1239`,`:1259`）なので、重みの次元は物量＝「石炭の重量」と「時計の個数」を比べている。単価の高い財は物量が小さいので構造的に労働を取れない。

**(B) 需要0の財では供給側の因子が代数的に無効になる。**
`prodW = D × Scale` は積なので `D=0` なら `Scale` は消える。`:385` で `fraction` は `LaborFloorMix/laborCount` という定数へ縮退し、`:463` の `Capacity` は `Scale` に依存しなくなる。**これが「Scale を 0.05→1.0 に播いても生産量0.0」の代数的正体**（実測は上表）。同時に `.Scale` の力学読み手は `:300`/`:304` の2行だけなので、**Scale は「取り分の付け替え」専用の量であり、州の総生産能力を1単位も動かさない**。

**(C) 「作りたい量に基づく発注」が唯一 `:1012` のトリクルにあり、それが価格を経由せずに現物を食う。**
下流の投入需要 `:1011 inputNeed += s.Output * eq` は**既に作っている量**にしか比例しない＝上流が止まる→下流が買えない→下流の産出↓→上流への需要↓ の自己閉鎖ループ。これを断つ唯一の経路が `:1012` で、`ReignitionTrickleConserves=0`（`Coefficients.cs:1963`）により `:1240` で coreDemand に全額算入され、実際に在庫を食い `LastSold` に紛れる（`:1432-1434`）。財収支 `Invariants` は緑のまま通るので**原理的に検知できない**。

### 一文にすると

> **需要の計算は壊れていない。「需要量」が価格を飛ばして労働配分器に直結していること（＝物量が価値のふりをしていること）と、「作りたい量に基づく発注」が価格ではなく現物で表現されていること、この2つが根である。**

作者の言う「幽霊生産」は、この2つの帰結として現れた**症状**であって原因ではない。だから外し方は「削る」ではなく「**需要から配分の仕事を取り上げ、価格に返す**」になる。

### 反証条件（これが出たら診断は誤り）

1. **決定的**：段3（準レント配分）を点火しても軍需 canary の Q1 小銃生産が中央値0.0のままなら、律速は配分の物差しではなく `:466 profitFactor` の乗算ゼロ（`price <= mc`）か `effFill` である。→ 診断(A)(B)は棄却。
2. 段0の計器で、同一労働プール内の `prodW` シェアが `LastDemand` ではなく `Scale` の分散でほぼ決まっている（＝`LastDemand` が財間でほぼ均一）なら、物量重みは律速でない。
3. 段0の反実仮想（`LastDemand` から `inputTrickle` を抜いたシェア）が現行シェアと1%も違わないなら、「現行の経済はこの需要の上に立っている」（`Coefficients.cs:1967`）は誇張であり、松葉杖の撤去は別の理由で難しいことになる。

## 2. 組み換えの中核 ― 準レント配分

### 2-1. 書き換える行

**`EconomyStep.cs:300-304` を1箇所だけ差し替える。`:383-386` の `fraction` 式には一切触らない。**

```csharp
var mk = region.Markets[s.GoodId];
if (coef.LaborRentWeight > 0)
{
    double mcW  = s.MarginalCost + InputCostPerUnit(s, region, coef);   // :464 と厳密に同一式
    double pW   = coef.ExportPriceInMargin > 0 ? RealizedPrice(mk, coef) : mk.Price;
    double rent = pW - mcW;
    if (!(rent > 0)) rent = 0;                       // 否定形＝NaN も 0 側へ倒す
    prodW[pi] = rent * s.UnitCapacity * s.Scale;     // 1労働シェアあたりの準レント×据付規模
}
else
{
    prodW[pi] = mk.LastDemand * s.Scale;             // 旧式をリテラルのまま false 側へ
    if (coef.ExportDemandWeight > 0)
        prodW[pi] += coef.ExportDemandWeight * mk.ExportSmoothed * s.Scale;
}
```

`s.UnitCapacity` は `:463` の積から `fraction` を除いた量を**前月に純記帳**したもの。`:463` は1文字も変えない：
```csharp
s.UnitCapacity = region.Pops[lp].Size * s.Productivity * boost * harvestMul * mineralMul;  // 追加の1行
s.Capacity     = region.Pops[lp].Size * fraction * s.Productivity * boost * harvestMul * mineralMul;  // :463 不変
```
（`:463` の掛順を変えると下位ビットが動き厳密恒等が壊れるので、別行で記帳する。`Producer` に `double` 1本追加＝`Model.cs:233-251` 付近。`savetest` 必須。）

`InputCostPerUnit`（`EconomyStep.cs:2349`）は既に `internal` で、`region.Markets[].Price` しか読まない純関数なので `:300` の位置から呼べる（`:464`/`:2105` に続く3回目の呼び出し＝生産者数×州数ぶんの計算増。性能影響は要実測）。

### 2-2. なぜこの式か（4つの必然）

- **`mc` が `:464` と同一式**＝「限界費用を賄えない生産者は産出も労働も取れない」が定義上一致する。今日は `:466 profitFactor=0`（作れない）なのに `:385` で床の労働を受け取る、という矛盾が常時起きている。
- **`× UnitCapacity`** ＝レントは「単位あたり」なので、労働1シェアあたりの価値を作るには潜在産出を掛ける必要がある。同じレントなら生産性が10倍の生産者が10倍の準レントを生む＝正しい配分。
- **`× Scale`** ＝建てた工場（`:2120` の `floor = max(ScaleFloor, BuiltScale)`）・倒産（`:2153 Scale=0`）・技術ゲート（`:2133 Scale=0`）が今日と同じ意味で重みに効く。
- **`Σfraction=1` は不変**。`:383-386` を触らないので `(1−床)×ΣprodW/ΣprodW + 床×(count/count) = 1` は厳密に成立し続ける。

### 2-3. 新しい定数を作らないことの証明

| 段 | 使う量 | 出所 |
|---|---|---|
| 段1 | `Stock / TargetStock` のカバー率 | `Model.cs:283` と `MarketFlow.cs:24`（既存2量）。クランプは 0/1（構造） |
| 段2 | `ReignitionTrickleConserves` | `Coefficients.cs:1963`（既存・0→1 のスイッチ） |
| 段3 | `Price − (MarginalCost + InputCostPerUnit)` | `EconomyStep.cs:464` と同一式 |
| 段3 | `UnitCapacity` | `:463` の積の部分（新しい数ではない） |
| 段3a | 実現価格の平滑率 | `ExportDemandSmoothing = 0.1`（`Coefficients.cs:1522`）を再利用 |
| 段4 | 発注量の時定数 | `SupplyAdjustSpeed = 0.15`（`Coefficients.cs:29`）を再利用 |

**`LaborRentWeight` は較正の自由度を持たない。** `fraction` は `prodW/laborTotalW` の比なので比例定数は完全に相殺する。意味を持つのは 0（休眠・厳密恒等）と正（点火）だけ。したがってこれは**構造スイッチであって係数ではない**（中間値で結果を選ぶ運用は合わせ込みに当たるので禁止する）。

## 3. 「上流から先に建てられる」機能の価格機構による置換 ― 最重要

### 3-0. まず正直に言うべき制約

`s.Capacity`（`:463`）に**資本の項が存在しない**。工場を建てる＝`BuiltScale`↑（`World.cs` 建設）→`:2120` の `floor`↑→`Scale`↑ で終わり、`Scale` の力学読み手は `:300`/`:304` だけ。**建設は州の総生産能力を1単位も増やさず、同じ労働プールの他の生産者から取り分を奪う行為として実現される。** クラスの docstring `EconomyStep.cs:7`（「工場能力＝min(労働能力, 資本×生産性)」）は実装と食い違っている。

したがって置換の目標は「上流に総量を足す」ではなく「**上流に労働を振り向ける因果を、幽霊需要ではなく価格で通す**」である。総量を増やしたいなら `Capacity` に資本項を入れる別ラウンドが要る（§7-3）。

### 3-1. 置換の4段（すべて既存の価格機構の内側）

**① 建設が初めて配分を動かす（段3の効果）**
`BuiltScale`↑ → `Scale`↑ → `prodW = rent × UnitCapacity × Scale`↑。**今日は `LastDemand=0` なら `Scale` をいくら上げても `prodW=0` で建設が無効**（実測：軍需 Q1 生産0.0）。準レントなら「価格が高い＝作れば儲かる」だけで労働が寄る。

**② 発注が価格を上げる（物は消えない）**
`Conserves=1` で `:1012` のトリクルは `:1240` の coreDemand から抜け、`:1259` の totalDemand にだけ残る。代数的に `totalDemand` は `Conserves` に**不変**（`(1−C)T` と `C·T` の和）なので、`:1261 m.LastDemand` は同月内で1ビットも変わらない。したがって `MarketFlow.cs:24` の `TargetStock` も `:68` の `eD` も `:74` の価格更新も同月内で恒等——**価格シグナルは1ビットも減らず、減るのは「物が消えること」だけ**。上流財の在庫が食われなくなるぶん、翌月以降は価格が正しく（高く）付く。

**③ 上流の準レントが立ち、労働が寄り、在庫が積む**
上流生産者は `rent = Price − mc > 0` を見て `prodW` を得る。誰もまだ現物を買っていなくても労働が来る。作られた物は買い手がいなければ `:1432 m.Stock = max(0, available − sold)` で在庫に残る＝**消えない**。

**④ 実在庫が下流を起動する（段1の効果）**
`:2006 fill = Math.Min(fill, ration[inp.GoodId])` の `ration` は `:1244` で `coreDemand > 1e-12 ? coreSold/coreDemand : 0` ＝**「需要0」と「供給0」を混同している**。`Conserves=1` にすると、買い手が発注しかいない財（専用中間財＝内燃機関125・装甲艦105・精密工作機械106など）は coreDemand=0 → ration=0 が確定し、下流の `fill=0` → `:485 target=0` の恒久デッドロックになる。**2026-07-31 の「ハーネス不合格10/10・上位軍需が全滅」（`Coefficients.cs:1966`）の機構的な根はここである。**

これを `1.0` で塗り潰すのは危険（「投入が無くても満額作れる」を広げる）。正しい代替は**在庫カバー率**——`:2006` だけをゲートで差し替える：

```csharp
double r = ration[inp.GoodId];
if (coef.NoOrderFillFromStock > 0 && !(coreDemandOf[inp.GoodId] > 1e-12))
{
    var im = region.Markets[inp.GoodId];
    double cover = im.TargetStock > Eps ? im.Stock / im.TargetStock : 0.0;
    if (!(cover > 0)) cover = 0.0;                     // 否定形＝NaN も 0 側へ
    if (cover > 1.0) cover = 1.0;
    r = cover;                                          // 誰も配給されていない＝制約は「在庫があるか」だけ
}
fill = Math.Min(fill, r);
```
`TargetStock`（`MarketFlow.cs:24`）は `max(TargetStockFloor, TargetStockBuffer × totalDemand)` で、**totalDemand には発注（トリクル）が今日から既に入っている**。つまり **`TargetStock` は既に注文帳として機能しており、新しいフィールドも新しい目標量も作る必要がない**。庫が満ちれば `cover=1` で下流が立ち上がり、空なら0のまま＝**無から有は一度も起きない**。

⚠この形は在庫主導案の中核だが、あちらの致命傷（`PlannedDraw` を `TargetStock` **本体**に加算すると `EconomyStep.cs:251/:280` の植民地輸入が対価なしに現物を湧かせる／`BilateralMarket.cs:304,420` の交易量が比例して膨らむ）を構造的に回避している——**`TargetStock` に何も足さないから**。

**⑤ 温まれば発注は自分で消える**
`trickle = max(0, ReignitionDemandFrac × DesiredOutput − Output)`（`:1012`）は `Output` が育つと0へ収束する。**恒久の松葉杖ではなく点火装置になる。**

### 3-2. 軍需 canary が決定的な理由（算出・未実測）

現状の因果（`docs\20260822\20260822_初期軍需の整合.md:369` の実測付き）：
国家が初期在庫を買う → 在庫枯渇 → 価格が参照の3〜25倍へ → `:919-927 PriceAfford` が閉じる → `militaryDemand≈0` → `LastDemand≈0` → `prodW=0` → 労働が来ない → 生産0 → 在庫が戻らない（永久ロック）。

このとき **`price/mc` は大きく、`:466 profitFactor` は 1.0 に飽和している**（`SupplySlope=0.5` なので `price/mc ≥ 1.5` で満額）。つまり**産出を止めている唯一の因子は `Capacity` であり、`Capacity` を止めている唯一の因子は `prodW=D×Scale=0` である**。準レントに替えると `rent = P − mc` が大きい軍需財に労働が雪崩れ、生産が始まり、価格が下がり、**`PriceAfford` を1文字も触らずにゲートが開く**。

→ **段3の合否判定はこれ1本でよい。開かなければ診断が誤り（§1の反証条件1）。**

## 5. 段階実装計画（4段・全段が既定0で厳密恒等）

**共通の硬性ゲート（1つでも赤なら差し戻し）**：405テスト緑／`Invariants` 破綻0／デッドロック0／`leakhunt` 清潔／`savetest` Q300／ハーネス不合格 0/10。

## 7. 作者に裁定を仰ぐ点

1. **作者裁定2026-08-01 の解除範囲。** `Coefficients.cs:1967`／`:1974` は「再点火の検討をしないこと」と明記されている。今回の指示（「幽霊生産を排除できる／不要な実装を削除するところまで」）を、この2つの恒久0裁定の**条件つき解除**と読んでよいか。読めない場合、本計画は段0（計器）で止まる。

2. **`ReignitionOrderSettles` の描写を失うこと。** 2026-08-01 に採用された「止まった工場の持ち主が持ち出しで再開準備を買い続ける／無一文なら再開の準備もできない」（`EconomyStep.cs:1018-1019`）は、段2で物が動かなくなると代金も消えるので失われる。(a) そのまま落とす、(b) 発注量そのものを財布で切る（`order = min(want, max(0,owner.Savings)/束単価)`＝pop消費の `:1223`/`:1229` と同じ2行）で置換する、のどちらか。(b) は「資金の無い国は再点火できない」を物理にするが、**貧困国ほど再点火できなくなる**という新しい非対称を生む。

3. **建設が総生産能力を増やさない件**（§3-0）。`Capacity`（`:463`）に資本項が無く、docstring `EconomyStep.cs:7` と実装が乖離している。今回の範囲に含めるか、別ラウンドか。**含めないなら「上位工場を先に建てる」は永久に「他財から労働を奪う」行為のままである**ことを明示的に受け入れる必要がある。

4. **`LaborFloorMix` は撤去か引き下げか。** 撤去すると「工場 0.15/111 対 職人 0.15/4＝27倍」の非対称（`Simulation.cs:939` vs `:963-976`）が同時に消え、**職人→労働者の没落（ラッダイト）の時期が大きく動く**。これは意図した副作用として受け入れるか。

5. **規模の経済の符号倒錯**（`EconomyStep.cs:459-461`）。`u = Output / LastDemand` は「規模」でなく自給率で、**内需が大きい国ほど生産性ボーナスが減る**。準レント化で `UnitCapacity` 経由にこの歪みが持ち込まれる。同ラウンドで分母を（国内＋輸出）へ是正するか、別件として残すか。

6. **実現価格（`RealizedPrice`）を入れるか。** 入れる利点は `ExportDemandWeight` の恣意的な 0.25 を削除できることのみ。**貿易量は原理的に動かない**（`貿易マップ:43-46` の構造天井）。輸出項を単純削除する（＝輸出が労働配分に届く経路が一時的に消える）案もあるが、それは比較優位の力を現状より**純減**させる。

7. **発注量 0.03 → `SupplyAdjustSpeed`（実質5倍）を採るか。** 市場外の固定率が消えるのは正しい方向だが、**`totalDemand` が膨らむ＝`LastDemand` が膨らむ**。`LastDemand` は `EconomyStep.cs:251/:280` の植民地輸入（`demandTarget = max(LastDemand, TargetStock) × …` → `m.Stock += import` ＝**対価なしの現物流入**）と `BilateralMarket.cs:304,420` の交易スケールを直接動かす。したがって 4b は単独バッチ必須で、植民地財の `LastImport` を必ず併読する。**安全策は 0.03 据え置き**（ただし市場外の固定値が1本残る）。

8. **`m.LastShortage`（`EconomyStep.cs:1436`）を配線するか。** 書かれているが SimCore に力学の読み手がゼロ（`:234`／`Diplomacy.cs:2613`／`MultiNationSim.cs:327`／`Politics.cs:827` はいずれもゼロ化のみ）。「需給の未充足量」という最も直接的な需要シグナルが空き端子のまま残る。今回は**新機構を足さない方針で見送る**提案だが、裁定を仰ぐ。

9. **基線の取り直し許可。** 2026-07-31 の `Conserves=1` 実測（10/10不合格）は決済点火（2026-08-01）前かつ段1前であり、**差し戻しの根拠に使えない**。段2の判定に使う基線を新規に取り直すこと。
